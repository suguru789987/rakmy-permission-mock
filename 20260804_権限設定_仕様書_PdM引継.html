2026-08-03 ／ ラクミー経営管理 ／ 対象: suguru789987/rakmy-permission-mock build eedfcd3（整合監査済み・20260803_08）

概要

「誰に何を見せるか」を顧客自身が設定できるようにする機能。 現行は権限が3種類固定で、顧客側に作る手段が無い。

やることは ① 権限を作る → ② 人に配る → ③ 点検する の3つだけ。

① 権限を作る            ② 人に配る                  ③ 点検する
┌──────────┐      ┌──────────┐      ┌──────────┐
│  権限一覧      │─────▶│  ユーザー割当   │─────▶│  役割サマリ     │
│              │      │              │      │              │
│ ＋新規作成     │      │ 誰に付けるか    │      │ 誰が何人持つか  │
└──────────┘      └──────────┘      └──────────┘
      │ ①ベースを選ぶ           │ 権限を1つ選ぶ            │
      │ ②権限名・区分           │ 担当店舗を選ぶ           │
      │ ③画面ごとに設定         │                        │
      ▼                       ▼                       ▼
   保存 ────────────────▶ 保存 ────────────────▶ 確認

最短の一本道

権限一覧 → ＋権限を新規作成 → ①ベース → ②権限名・区分 → ③画面ごとに設定
        → 「ユーザー割当で紐付け →」 → 対象者と担当店舗を選ぶ → 保存 → 役割サマリで確認
ステップ 画面 やること 決まること
① 権限編集 近いテンプレートを選び、画面ごとに 操作／閲覧／なし を設定 どの画面を見せるか
② ユーザー割当 権限を1つ選び、担当店舗を紐付ける 誰が・どの店のデータを扱えるか
③ 役割サマリ 権限ごとの許可数と割当人数を確認 抜け・持たせすぎの検知

押さえるべき3点

  1. 権限はロール経由で配る — 人に直接付けない。「店長」を1つ作れば店長が10人でも設定は1つ（→ §7-A）
  2. 権限と担当店舗は別々に決める — 権限＝どの画面、担当店舗＝どの店のデータ。同じエリア長でも人ごとに店舗数が違うため（→ §7-B）
  3. 1人1ロール — 付け替えると前の権限は外れる。兼務は専用の権限を作って表現する（→ §3.5・暫定決定）

入口が複数ある画面（権限編集は4入口、割当は3入口）があり、来た元によって戻り先が変わる。全26フローは §5.6。

1. 背景と課題

1.1 現行の制約

現行ラクミー経営管理の権限は master / manager / shop_manager の3種類固定。DBに権限テーブルは無く、アカウント種別で分岐している。顧客側で権限を作る手段は存在しない。

1.2 顧客要望の実態

CSに寄せられる要望は「3権限の中間」に集中する。

要望 現行で応えられるか 不足しているもの
経理担当に全社のお金は見せるが給与は見せない ✕ 画面単位の制御
エリアマネージャーに担当2店舗だけ見せる ✕ データ範囲の制御
顧問税理士に閲覧だけさせる ✕ 操作（書込）の制御
アルバイトリーダーに売上だけ見せる ✕ 画面内の指標単位の制御

4つの要望が要求する制御軸がすべて異なる点が重要。これが §3 の権限モデルが4軸（画面／機能／指標／データ範囲）になっている理由であり、§4 の段階導入の順序を決めている。

1.3 なぜ今やるか

多店舗顧客の受注条件になっている案件がある。また「権限が分けられないので本部の一部しか使っていない」状態は利用率が上がらず、更新時に解約リスクとなる。

2. スコープと用語

2.1 スコープ

対象 — 会社画面（経営管理 V69）の権限設定機能。権限の定義、ユーザーへの割当、担当店舗の紐付け、指標の可視性設定。

対象外 — 新しい画面カテゴリ自体の追加（プロダクト側のマスタ機能）。タイムレコ側の権限。従業員台帳の管理。

2.2 用語定義

用語の揺れが議論を壊すため、以下で固定する。

用語 定義 誤用されやすい点
権限（ロール） 「どの画面をどこまで使えるか」の定義。名前を持つ 「役職」と混同される
区分 権限が会社画面向きか店舗画面向きか（会社／店舗の2値） 「データ範囲」と混同される
データ範囲（スコープ） どの店舗のデータ行を扱えるか（自店舗／指定店舗群／全社） 「区分」と混同される
割当 権限をユーザーに適用する行為 —
役職 従業員台帳の肩書き（店長・スタッフ等）。権限を決めない参考情報 権限だと誤解される
カテゴリ 権限設定の単位となる画面のまとまり。27個 —
機能 カテゴリ内の個別機能。53個 —
指標 分析画面に表示される数字の項目 —

区分とデータ範囲は独立した別軸である。「店舗ロールだから自店舗のみ」ではない。区分は画面の出し分け、データ範囲は行の出し分けで、組み合わせは自由。

3. 権限モデル

3.1 4つの制御軸

軸 制御するもの 設定場所 実装段階
① 画面 どの画面を開けるか 権限編集 今回
② 機能 画面内で何ができるか（なし／閲覧／操作） 権限編集（画面名クリックで展開） 次
③ 指標 画面内にどの数字を出すか 指標一覧／指標条件設定 後
④ データ範囲 どの店舗の行を返すか ユーザー割当（担当店舗） 後

3.2 権限レベル（3状態）

ダッシュボードは閲覧固定で権限設定の対象外。 ランディング画面のため「なし」に設定できない。全項目オフの権限でもログインでき、ダッシュボードに着地する（→ AC-13）。したがって「許可していない画面は開けない」（AC-11）の対象からも外れる。

なし ⊂ 閲覧 ⊂ 操作 の順序権限。操作＝登録・編集・削除を一体で含む書き込み全般。

機能の性質により取りうる段階が異なる。

種別 段階 例
常時(base) 閲覧固定 ダッシュボード
閲覧専用(view) なし／閲覧 売上分析・集計
設定(edit) なし／閲覧／操作 納品書・棚卸・従業員管理
管理(admin) なし／閲覧／設定可 会社情報・お支払い・連携設定
実行(action) なし／実行可 ダウンロード

削除を別権限に分けていない。 「登録できる＝編集も削除もできる」とし、破壊的な削除は実行時の確認ダイアログで担保する。分けると状態が4つになり、設定コストが跳ね上がる割に「登録はできるが削除はできない」の実用ケースが乏しかったため（→ §7-D）。

3.3 カテゴリ構成（27カテゴリ53機能）

カテゴリは ctx により3種に分かれ、区分によって出し分ける。

ctx 意味 数 カテゴリ
common 会社・店舗どちらでも 17 ダッシュボード／売上分析／仕入分析／詳細分析／集計／従業員（閲覧）／締め状況（閲覧）／ダッシュボード（カスタマイズ）／ラベル／納品書／売上／棚卸／小口現金／従業員管理／締め管理／ユーザー／店舗間商品移動
company 会社画面のみ 4 ダウンロード／店舗（管理）／会社情報／お支払い
shop 店舗画面のみ 6 発注先&仕入商品／店舗情報／連携設定／費用設定／休業日設定／予算設定

区分＝会社 → 21カテゴリ（common 17 ＋ company 4）／区分＝店舗 → 23カテゴリ（common 17 ＋ shop 6）。

機械可読の辞書は docs/feature_keys.json（category_count: 27 / feature_count: 53）。機能を増減したらこのファイルと ENFORCEMENT.md 付録Aを再生成すること（カウント整合が崩れると検証の網羅判定が壊れる）。

3.4 ロール構成

ロール 区分 位置づけ
オーナー（全権） 会社 全権固定・編集不可。権限一覧から除外
会社ロール（経理／人事など） 会社 職務分掌で設定
店舗ロール（店長／従業員） 店舗 店舗現場。既定はこの2つ。エリア長などはここから派生させる

エリア長は既定テンプレートに含めない。 現時点で店長と権限差はなく、顧客の組織によって要否も内容も変わるため、店長をベースに顧客が作るカスタマイズ例として扱う。上位の役割という位置づけでもない。差別化が要る場合は権限編集で画面を絞る／広げる、または担当店舗数で行う。

既定テンプレートは オーナー／本部管理／店長／従業員の4種（＋ゼロから作る「まっさら（なし）」）。

3.5 1人1ロール（2026-08-03 決定・暫定）

副作用：会社画面と店舗画面の両方を扱う職務は、1つの権限で表現できない（2026-08-05 判明）。 区分は会社／店舗のどちらか一方しか選べず、1人が持てる権限は1つのため。たとえば経理は「お支払い（会社画面）」と「費用設定・予算設定（店舗画面）」の両方を見るが、「経理（会社）」と「経理（店舗）」の2つを作って人を分ける運用になる。エンジニアからの指摘で判明した。→ AC-34（次段階）・AC-22（SC-01a／SC-01b に分割）

1人が同時に持てる権限は1つ。付け替えると前の権限は自動的に外れる。

採用理由 — 「この人は結局何が見られるのか」が権限名だけで確定する。合算方式では権限名を見ても実際の可視範囲が分からず、点検が困難になる。

副作用 — 兼務（店長 兼 本部経理など）は「店長＋経理」という権限を新設して表現する。兼務の組み合わせだけ権限が増える。

この判断は暫定である。 運用して権限が増えすぎるようなら合算方式への回帰を検討する。判断材料は「実際に作られた権限の数」と「そのうち兼務用が何割か」。→ §8-1

4. 段階導入

権限は誤って塞げば業務停止、誤って通せば情報漏洩。どちらも重大なため、blast radius の小さい順に入れる。

段階 内容 リスク 状態
P0 データモデル＋保存＋シャドー検証 低 未着手
P1 画面単位の閲覧制限 低〜中 ステージング検証中
P2 操作（登録・編集・削除）判定 中 未着手
P3 データ範囲の強制 高 未着手
P4 指標の可視性 中 未着手
P5 監査ログ・ロックアウト防止・移行 中 未着手

各段階はシャドー検証 → 部分有効化 → 全面の3段で進める。詳細は ROADMAP.md。

既存顧客への影響を無くすため、リリース時に現行3権限と同じ動作のプリセットを用意する。 これが移植の要件であり、受入条件 AC-01〜04 に対応する。

P1 リリース時点の到達度（重要）

必須の受入条件をすべて満たしても、顧客要望4つのうち満たせるのは1つだけ。 §1.2 の4要望はそれぞれ別の制御軸を必要とし、P1 は「画面」しか実装しないため。

顧客要望 必要な軸 受入条件 P1で満たせるか
経理に金は見せ人は見せない 画面 AC-10 / AC-11 ○
エリアマネージャーに担当店だけ データ範囲 AC-23 ✕（P3）
税理士に見るだけ 操作 AC-24 ✕（P2）
売上だけ見せ原価は隠す 指標 AC-25 ✕（P4）

したがって AC-22（意図判定）の必須ラインは「画面単位で表現できる4シナリオに×を出さない」までとし、データ範囲・操作を要する SC-03／SC-05 は AC-32（次段階） に分けている。P1 の合格＝MVP 達成ではない。この差を曖昧にすると「受入条件を全部満たしたのに顧客が使えない」という事態になる。

検証で SC-03／SC-05 が × と確定した時点が、P2／P3 を前倒しするかの判断ポイント（→ §8-6）。

5.2 権限編集（統合ウィザード）

新規作成と既存編集で同じ画面を共有し、タイトルとステップ番号を出し分ける。

モード ステップ
新規 ①ベース → ②基本設定（権限名・区分） → ③権限内容
編集 ①基本設定 → ②権限内容（ベース選択は非表示）

ステップ順は「識別 → 中身 → 確定」で固定。 区分を先に決めるのは、区分が③に出る画面リストを絞るため（会社なら店舗専用6画面が出ない）。逆順にすると設定後に区分変更でやり直しになる。

名前を変えて保存するときは、上書きか新規かを選ばせる（2026-08-14 決定）

選択 挙動
上書きする 同じ権限の名前が変わる（識別子は不変）。その権限を持つ全員がそのまま新しい名前の権限を持つ。元の名前は残らない
新しい権限として保存 元の権限をそのまま残し、新しい権限を1件追加する。既存の割当は元の権限のまま

却下案 — 黙って上書きする（当初の実装）。「エリア長」を直して「西エリア長」にしたい顧客は、元のエリア長も残したい場合がある。黙って上書きすると、派生を作ったつもりが元を失う。名前を変えたときだけ聞く形にし、画面設定だけを直した場合は従来どおり上書きする。→ AC-40

なお名前が既存と重複する場合は、どちらを選んでも保存できない（→ AC-38）。

編集時はベース選択を出さない。 土台を選び直すとそれまでの設定が丸ごと上書きされ、どこを自分で直したのか分からなくなるため。土台から作り直したい場合は新規作成する。

権限名は一意（2026-08-13 決定） — 既存と同じ権限名では保存できず「別名で保存してください」を出す。同名が並ぶと割当時にどちらを選ぶか判別できないため。→ AC-38

区分は保存後に変更できない（2026-08-13 決定） — 編集モードでは区分を非活性にする。区分を変えると③の画面リストが入れ替わり、既存の設定値が意味を失う（何が残り何が消えたか追えない）。別区分が必要ならカスタマイズテンプレから元の権限を選んで設定を引き継ぎ、新規作成する。→ AC-39

ベース候補

カスタマイズテンプレ 顧客が作った権限（経理担当・エリア長 など）。既定テンプレと同名のものは出さない
新規作成 新規作成（全機能なし）

3階層にした理由（2026-08-14 決定） — 「既定で用意したもの」と「自社で作ったもの」は選ぶときの意味が違う。前者は迷ったら選ぶ土台、後者は自社の運用に合わせて育てた資産。顧客が作った権限がそのまま次の土台になる構造を、グループ名で示している。エリア長を一度作れば、次からは「カスタマイズテンプレ」に並ぶ。

ゼロから作らせない設計。 27画面53機能をゼロ設定するのは非現実的なため、必ず「近いものを選んで差分を直す」形にしている。リリース時の移植プリセットがそのままベース候補になる想定。

最下部のコミット領域 — 「🔗 ユーザー割当で紐付け →」CTA ＋ 保存／キャンセル。権限編集はスコープ（担当店舗）を扱わない（→ §7-B）。例外はガバナンス警告（店舗ロールで店舗未設定の保持者がいる時のみ）。

5.3 権限一覧

ロール × カテゴリのマトリクス。一覧画面権限（青）／設定画面権限（緑）の2タブ。

  • 既定は折りたたみ（要約列のみ）。27画面を全部出すと横に長大になり読めないため
  • 「👤 表示ロール」で行を絞る／「📌 権限列設定」で列を選ぶ。列選択は localStorage に記憶
  • セルクリック → 権限編集の該当カテゴリへズーム＋一時ハイライト。気づきから修正までを一続きにする
  • ヘッダーの会社名プルダウンで会社／店舗スコープを切替。行（ロール）と列（画面）が同時に追従する
  • オーナーは一覧から除外。専用操作は右上「👑 オーナー操作」に集約

権限の削除（2026-08-13 決定） — 権限一覧の各行から削除できる。割当ユーザーが1名以上いる権限は削除できず、保持者名を挙げた警告を出す。 消した瞬間にその人が未割当になり、ログインしても何も見えなくなる（業務停止）ため。先に割当を外すか別の権限に付け替えてから削除する。オーナー（全権固定）には削除の導線を出さない。削除時は指標一覧側の該当列も同時に落とす。→ AC-35

5.4 ユーザー割当・割当編集・一括割当

割当の入口は3つ（意図的に共存）

思考の出発点が3通りあるため。ただし付与の実体は割当画面に集約しており二重管理は無い。

割当編集 — 権限はラジオで1つ（先頭に「割当なし」）。別の権限を選ぶと「選ぶと『○○』から置き換わります」を行に表示。店舗ロールを選んだ時のみ店舗ピッカーが出る。

7. 設計判断の記録（なぜそう決めたか）

引き継ぎで最も失われやすい情報。 各判断には却下した案とその理由を残す。

A. 権限はロール経由で与える（人に直接付けない）

却下案 — ユーザーごとに権限を作り込む。

理由 — 従業員が増えるほど設定が増殖し、「誰がどこまで見えるか」の把握が不可能になる。「店長」を1つ作れば店長が10人でも設定は1つで、修正も一箇所で済む。

関連 — この原則があるため、§8-2（ユーザー行からの権限編集）が論点になる。

B. 担当店舗は割当側にのみ持たせる

却下案 — 権限編集にも「データ範囲」の選択肢を置く（当初はあった。撤去した）。

理由 — 両方に店舗設定があると「どちらが本当か」が分からず、片方だけ直して事故る。同じ「エリア長」でもAさん2店舗・Bさん3店舗なので、権限側に持たせると担当店舗の組み合わせだけ権限が必要になり破綻する。

徹底の度合い — 権限編集③から掌握店舗数・店舗名の情報表示すら撤去した。割当由来のデータを権限定義の場に出さない。例外はガバナンス警告のみ。

C. 区分とデータ範囲は独立した別軸

却下案 — 「店舗ロール＝自店舗のみ」と固定する。

理由 — 「従業員だが複数店舗に所属」「店舗ロールだが全社データを見る」といった実運用がある。ロール定義の区分・範囲は既定値（テンプレ）にすぎず、実効スコープは割当で束縛する。

「全店」は動的（2026-08-13 決定） — 店舗が追加されたとき、「全店」を選んでいる人の対象に自動で含まれる。スナップショット案（選んだ時点の店舗を保持）は、新店舗が見えず業務が止まるため却下した。ただし誰の操作も無く閲覧範囲が広がるため、ヘルプページに明示することを受入条件に含めている。特定店舗だけを見せたい場合は「全店」ではなく個別に選ぶ。→ AC-36

店舗の閉店・削除は不活性化（2026-08-13 決定） — 物理削除せず、担当店舗の紐付けは保持する。物理削除すると担当店舗が0件になり、「店舗ロールは1件以上必須」（AC-19）と矛盾する状態が生まれるため。→ AC-37

D. 操作＝登録・編集・削除を一体（削除を分けない）

却下案 — 4状態（なし／閲覧／操作／全て（削除））＋操作詳細トグル。実際に実装したが撤去した。

理由 — 状態が増えるほど設定コストが跳ね上がる割に、「登録はできるが削除はできない」の実用ケースが乏しかった。破壊的な削除は実行時の確認ダイアログで担保する方が実効的。

D'. 画面カテゴリを追加したときの既定は「なし」（fail-closed）

却下案 — 追加した画面を既存の権限でも見えるようにする（利便性優先）。

理由 — 画面が増えるたびに全員の閲覧範囲が黙って広がる。顧客は増えたことに気づけない。既定は必ず安全側（なし）とし、必要なら顧客が明示的に許可する。動作テストでは検出できないため、コード上の既定値をエンジニアと確認する。→ AC-12・T-24

E. 機密ランクを画面に出さない

却下案 — 指標に🔓🔸🔒バッジを表示する。実装したが撤去した。

理由 — バッジを出すと顧客が指標を選ぶたびにランクの妥当性を判断させることになる。ランクは初期値の自動決定にのみ使い、画面はシンプルなON/OFFスイッチにする。

F. 会社指標を店舗ロールに出すことを禁止しない

却下案 — 店舗ロールには全社集計をハードブロックする。当初そうしていたが撤回した。

理由 — 「うちは店長にも全社利益を見せる」という顧客がいる。既定OFF＋管理者オプトインとし、ハードブロックはしない。ただし行データの遮断は独立にハード強制する。

G. 「含める」チェックを店舗選択と統合しない

却下案 — 一括割当で店舗を選んだら自動的に権限を付与する。

理由 — 誤クリックがそのまま権限付与になる。明示チェックを安全装置として残す。会社ロールは対象店舗が無いため「含める」が唯一の付与手段でもある。

H'. エリア長を既定テンプレートにしない（2026-08-04）

却下案 — エリア長を既定の推奨テンプレートに含める（当初はそうしていた）。

理由 — エリア長は現時点で店長と権限差がない。差が出るのは担当店舗数だけで、それは割当で決まる（→ §7-B）。中身が同じテンプレートを2つ並べると、顧客は「どちらを選ぶべきか」を判断できない。さらにエリア長という役割の要否も内容も顧客の組織構造に依存するため、標準として提示すると「エリア長はこういうものだ」という誤った既定を押し付けることになる。

扱い — 店長をベースに顧客が作るカスタマイズ例として位置づける。運用デモには作成済みの例として残し「こう作れる」を見せる。既定テンプレートは オーナー／本部管理／店長／従業員 の4種。

H. 1人1ロール（2026-08-03・暫定）

却下案 — 複数ロール保持＋合算（当初の設計）。

理由 — 権限名だけで可視範囲が確定する。合算方式は点検が困難。

副作用を認識した上での暫定決定。 → §8-1

8. 未決事項（後任PdMの判断が必要）

8-1. 1人1ロールを継続するか【優先度：中・期限＝運用開始3ヶ月後】

論点 — 兼務のたびに専用権限が増える。増えすぎると権限一覧が読めなくなり、当初の課題に回帰する。

判断材料 — 顧客ごとの権限総数、うち兼務用の割合。10権限を超え、その3割以上が兼務用なら合算方式への回帰を検討。

準備 — DB制約で1人1ロールを縛らない（アプリ層のみ）。縛るとマイグレーションが必要になる。

8-2. ユーザー行からの権限編集をどう扱うか【優先度：高・期限＝実装前】

論点 — 「田中さんだけ調整したい」でユーザー行から権限編集に入ると、同じ権限を持つ全員に波及する。事故になる。

選択肢

案 内容 副作用
A 権限名の変更を強制（＝その人専用の権限を作る） 権限が人数分に増殖し §7-A が崩れる
B 警告のみ（「他に○名が持っています」＋続行／複製を選択） 無し。複製を選べばAと同じ結果
C ユーザー行からは編集させない 遠回りになる

推奨は B。 事故を防ぎつつ権限の増殖も起きない。

8-3. 権限一覧をマトリクスから一覧に変えるか【優先度：中・期限＝UI確定前】

論点 — 現行はマトリクス（権限×27画面）。シンプル一覧（区分・権限名・操作）にする案がある。

トレードオフ — マトリクスは権限同士を横並びで比較できるが横に長い。一覧は権限数が増えても崩れないが、可視範囲は別途ボタンで確認することになる。

併存案 — 既定は一覧、「比較表示」でマトリクス。

連動 — この判断でタブの階層が決まる。一覧化するなら「権限／ユーザー」の1階層で済む。マトリクス維持なら2階層になる。

8-4. 割当対象は全従業員かログイン管理者か【優先度：高・期限＝実装前】

論点 — 現行は「経営管理にログインする管理者」のみを対象にしている。全従業員（アルバイト含む）を並べる案がある。

懸念 — 全従業員だとログインしない人まで一覧に出て、誰に権限を付けるべきかが埋もれる。全従業員にするならログイン可否のフィルタが別途必要。

8-5. 権限設定をチェックボックス（2値）にするか【優先度：中・期限＝P2着手前】

論点 — 今回は閲覧制限のみなので2値で足りる。ただし P2（操作制限）で「閲覧はできるが操作はできない」が必要になり、3状態が要る。

判断 — 今2値にして P2 で作り直すか、最初から3状態にするか。

8-6. 検証で確定させる3点【優先度：高・期限＝検証完了時】
